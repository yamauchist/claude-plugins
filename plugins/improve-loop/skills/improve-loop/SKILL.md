# improve-loop

リポジトリ（または指定された範囲）を、サブエージェントによる「洗い出し」と「修正」を交互に繰り返して改善する。

ラウンドごとに**担当エージェント**を 1 体、新しく起動する。担当エージェントは、まず改善点を洗い出し、続けて同じエージェントのまま修正も行う。洗い出しで読んだコードの文脈をそのまま修正に使えるので、読み直しの手間とトークンが省ける。次のラウンドでは、新しい目で見させるために、また新しい担当エージェントを起動する。

メインの Claude は進行役に徹し、自分では洗い出しも修正もしない。役目は、指摘の仕分け、台帳の管理、ユーザーへの相談、修正結果の確認である。

## 対象範囲

- 既定は**リポジトリ全体**。
- ユーザーが「ここを見て」「`src/api` だけ」「README まわり」などと範囲を示したら、それを**対象範囲**とし、洗い出しも修正もその範囲に限る。範囲外の問題に気づいた場合は修正せず、最後の報告で「範囲外の気づき」として挙げるだけにする。
- ユーザーが観点（「性能を中心に」「ドキュメントだけ」など）を示したら、それも洗い出しの依頼に含める。

## 準備（最初に 1 回）

1. **作業ツリーを確かめる**：`git status` と現在のブランチを見る。
   - git リポジトリでなければ、ループを始めない（修正の確認、巻き戻し、コミットがすべて git に頼るため）。`git init` してよいかをユーザーに聞き、応じなければ始めない。`git init` したら、今のファイルを最初のコミットに入れてよいかも聞く（入れないと、すべてが開始時の未追跡ファイルになり、洗い出しと修正の対象外になるため）。
   - 最初のコミットを断られた場合や、HEAD がない（コミットが 1 つもない）場合は、ループを始めずにその旨を伝える（対象がなく、修正の確認と巻き戻し、最終報告のコミット一覧もできないため）。
   - 未コミットの変更があれば、ループのコミットに混ざってしまうので、先にユーザー自身でコミットするか退避してもらう。未追跡ファイル（`git status --porcelain` の `??` の行）は対象外とし、そのまま始めてよい。
   - 既定ブランチ（`main` など）にいる場合は、作業用ブランチ（例：`improve-loop/<日付>`）を切ってよいかをユーザーに聞く。断られたら、どのブランチで作業するか（既存のブランチ名を指定してもらう、または中止する）を聞き直す。既存のブランチを指定されたらそこに切り替え、中止と言われたら始めない。既定ブランチに直接コミットするのは、この聞き直しの答えとしてユーザーが既定ブランチを明示したときだけとする。切り替えが未追跡ファイルとの衝突（切り替え先で追跡されているファイルが、今は未追跡で置かれている）で失敗したら、その旨をユーザーに伝えて対処してもらい、それまで始めない。
   - 作業するブランチに切り替えたあとで、`git status --porcelain --untracked-files=all` の `??` の行（未追跡ファイルの一覧）を、台帳の「開始時の未追跡ファイル」に控える（切り替えで未追跡ファイルの一覧が変わることがあるため、切り替えの前には取らない）。`--untracked-files=all` を付けるのは、付けないと未追跡のディレクトリが `?? dir/` の 1 行にまとまり、その中に作られた新規ファイルを見分けられないためである。修正の確認では、この一覧にない `??` だけを新規ファイルとして扱う。この一覧のファイルは、対象範囲の中にあっても洗い出しと修正の対象外とする（変更されても `git diff` に出ず、`git restore` でも戻せないため）。
   - `git log --oneline -20` でコミットメッセージの書き方（言語、接頭辞の有無、文体）をつかんでおく。
2. **台帳を作る**：リポジトリの外（スクラッチパッドがあればそこ、なければ OS の一時フォルダ）に `improve-loop-ledger.md` を作る。リポジトリの中には作らない。書式は下の「台帳」を参照。会話が長くなって文脈が要約されても、台帳を読み直せば続きから再開できる。
3. **開始を告げる**：対象範囲、観点、止め方（いつでも「止めて」と言えば、依頼済みの修正が終わった時点で止まり、新しい修正やラウンドは始めない）を 1〜2 行で伝え、すぐにラウンド 1 を始める。

## コミット

修正は、確認が済んだものから**適切な単位で**コミットしていく。コミットするのはメインで、担当エージェントにはコミットさせない（差分を確かめてから入れるため）。

- **単位**：1 コミット = 1 つのまとまった変更。原則として指摘 1 件で 1 コミットにする。同じ原因から来る複数の指摘や、同じ箇所を直す指摘は 1 コミットにまとめてよい。逆に、無関係な指摘を「ついでに」まとめない。
- **時機**：修正の差分を確かめて問題がなければ、その場でコミットする。ラウンドの終わりまで溜めない。直せなかったもの、差分がおかしいものはコミットせず、変更されたファイルを `git restore --staged --worktree --source=HEAD -- <パス>` で戻してから台帳に「失敗」と書く（`--staged` を付けるのは、ステージされた変更も戻すため）。まとめて頼んだ単位の一部だけが失敗したときは、先に問題のない単位をコミットし、そのあとで失敗した単位が変更したファイルだけを `git restore --staged --worktree --source=HEAD -- <パス>` で戻す（パスなしや `.` では戻さない。ほかの単位の修正まで消えるため）。`git restore` は新規ファイルを消さないので、その単位の修正で新しく作られたファイルは `git clean -f -- <パス>` で消す。`git clean` は必ずパスを指定して使い、パスなしでは実行しない（その単位と無関係な未追跡ファイルまで消えるため）。台帳の「開始時の未追跡ファイル」にあるパスには `git clean` を使わない（ユーザーのファイルを消してしまうため）。
- **分け方**：担当エージェントには、コミット単位ごとに修正を頼む。単位どうしが別々のファイルしか触らないなら、まとめて頼み、終わったらファイルごとに `git add <パス>` で分けてコミットしてよい。同じファイルを触る単位が複数あるときは、1 単位ずつ頼んで、そのつどコミットしてから次を頼む。まとめて頼んだのに、報告で複数の単位が同じファイルを触っていたとわかったら、そのファイルを `git restore --staged --worktree --source=HEAD -- <パス>` で戻し（新規ファイルなら上の「時機」の手順どおり `git clean -f -- <パス>` で消し）、それらの単位を 1 単位ずつ頼み直す。
- **ステージ**：ステージするのは、担当エージェントの報告に載った、その単位のパスだけとし、`git add <パス>` で行う。`git add -A` や `git add .` は使わない（テストやビルドの成果物など、どの単位にも属さないファイルまでコミットに混ざるため）。新規の未追跡ファイル（`??` の行のうち、台帳の「開始時の未追跡ファイル」にないもの）で、どの単位の報告にも載っていないものは、何が作ったかを担当エージェントに確かめる。テストやビルドの成果物なら、開始時にはなかったファイルなので `git clean -f -- <パス>` で消してからコミットに進む（「開始時の未追跡ファイル」にあるパスは消さない）。説明がつかなければ、そのファイルを作った可能性のある単位を失敗として扱う。
- **メッセージ**：準備で見た既存の書き方に合わせる。何をなぜ直したかを書き、台帳の ID は本文に入れてよい。
- push はしない。最後の報告で、コミットの一覧を示す。

## 1 ラウンドの流れ

### 1. 洗い出し（毎回、新しい担当エージェント）

Agent ツールで、そのラウンドの担当エージェントを**新しく**起動する（`subagent_type: general-purpose`、`run_in_background: false`（結果を待つため））。修正もこのエージェントに頼むので、編集ツールを持つ種類を選ぶ。前のラウンドの担当エージェントに洗い出しを頼むことはしない。新しい目で見させるためである。

結果に含まれる**エージェント ID を控えておく**。このラウンドの修正は、すべてこの ID 宛てに SendMessage で頼む。

依頼文は [references/prompts.md](references/prompts.md) の「洗い出しの依頼」を使う。この段階ではまだファイルを編集させない（仕分けの前に直されると、要判断の指摘まで勝手に直ってしまうため）。台帳から次の 4 つを必ず渡す。

- **対応済み・見送り・保留中・失敗・却下の指摘の一覧**（同じ指摘を繰り返させないため）
- 対象範囲と観点
- 開始時の未追跡ファイル（対象外にするため）
- 記録済みの範囲外の気づき（同じ気づきを繰り返させないため。なければ「なし」）

### 2. 仕分け

返ってきた指摘を、メイン自身が 1 件ずつ確かめて仕分ける。担当エージェントの分類は参考にとどめ、うのみにしない。必要なら該当箇所を自分で読む。重要度（高・中・低。目安は [references/prompts.md](references/prompts.md) の「洗い出しの依頼」）も、担当エージェントの評価をうのみにせずメインが確かめ、必要なら付け直す（終了条件の判定に使うため）。

| 区分 | 当てはまるもの | 扱い |
| --- | --- | --- |
| **自動修正** | 正解が 1 つに決まり、誰が直しても同じ結果になるもの。明らかなバグ、誤字、壊れたリンク、コードと食い違うドキュメント、使われていない import、明白なエラー処理の漏れなど | すぐ修正を依頼する |
| **要判断** | 振る舞い・仕様・公開 API・設定の既定値が変わるもの。妥当な直し方が複数あるもの。ファイルや機能の削除。依存パッケージの追加・更新。大きな構成変更。好みや方針の問題 | 保留キューに入れる |
| **却下** | 誤検知、すでに直っているもの、台帳の指摘の言い換え、効果に比べて変更が大きすぎるもの | 台帳に理由を書いて捨てる |

迷ったら**要判断**に倒す。ユーザーの意図と違う変更を勝手に入れるほうが、相談が 1 件増えるより損が大きい。

対象範囲の外の問題は、どの区分にも入れない。担当エージェントの「範囲外の気づき」や、指摘として挙がった範囲外の問題は、台帳の「範囲外の気づき」に書き写すだけにして、修正しない。

### 3. 自動修正（同じ担当エージェントに続けて頼む）

自動修正に仕分けた指摘を、控えておいた ID 宛てに SendMessage で送り、担当エージェントに直させる（依頼文は [references/prompts.md](references/prompts.md) の「修正の依頼」）。新しいサブエージェントは起動しない。SendMessage が遅延ツールとして名前だけ載っている場合は、ToolSearch（`select:SendMessage`）で読み込んでから呼ぶ。

- 指摘は自分が挙げたものなので、ID と題名、修正方針を伝えれば足りる。仕分けで方針を変えたもの（担当エージェントの修正案と違う直し方にするもの）は、その旨をはっきり書く。
- 自動修正の対象外にした指摘（要判断・却下）は、「今は直さない」と明記して渡す。
- 送る前に、指摘をコミット単位に分ける（上の「コミット」を参照）。
- 担当エージェントが終わったら、メインが差分（`git diff HEAD`。ステージされた変更も含めて見るため `HEAD` を付ける）を見て、指摘どおりに直っているか、余計な変更が入っていないかを確かめる。`git diff HEAD` は新しく作られた未追跡のファイルを表示しないので、`git status --porcelain --untracked-files=all` も見て、新規ファイル（`??` の行のうち、台帳の「開始時の未追跡ファイル」にないもの）がないか、あれば中身が妥当かを確かめる（どの単位の報告にも載っていない新規ファイルは、上の「コミット」の「ステージ」の手順で扱う）。テストやリンターがあれば担当エージェントに走らせ、その結果を受け取る。問題がなければ、コミット単位ごとにコミットする。
- 直せなかったもの、直した結果がおかしいものは、変更を戻し、台帳に「失敗」と理由を書く。そのうえで、その場で保留キュー（要判断）にも入れ（ID は変えない）、次の相談でユーザーに方針を聞く。保留キューには、場所・問題・失敗の理由と、直し方の案（別の直し方など）を書き写す。相談の結果、直したものや見送ったものは、「失敗」から「対応済み」や「見送り」に移す。
- 担当エージェントが「指摘が誤りだった」と報告したら、メインが該当箇所を読んで確かめる。誤りなら台帳の「却下」に移し（ID は変えない）、確かめられなければ「失敗」とする。
- 担当エージェントを続けられなかった場合（SendMessage が使えない、エラーで止まったなど）に限り、新しいサブエージェントを起動して直させる。依頼文は [references/prompts.md](references/prompts.md) の「修正の依頼」の形を使い、前のラウンドの指摘と同じく、場所・問題・修正方針をすべて書き写す。新しいエージェントの ID は台帳の「担当エージェント ID」に書き直し、そのラウンドの以後の修正（相談後の修正も含む）は新しいエージェントに頼む。

### 4. 保留と相談

要判断の指摘は**保留キュー**に入れる。入れるときは、洗い出しの報告から場所・問題・各案（利点と欠点）を台帳に書き写しておく。後のラウンドの担当エージェントに修正を頼むときや、文脈が要約されたあとに再開するときに、台帳だけで足りるようにするためである。報告に案がない指摘（担当エージェントが「ユーザー判断: 不要」としたがメインが要判断に回したものや、修正に失敗したもの）は、メインが該当箇所を読んで案を 1〜3 個作り、利点と欠点を添えて台帳に書く。作れないときは、担当エージェントに SendMessage で案を出させる。キューが **4 件**に達したら、そのラウンドの自動修正を終えてから、ユーザーに相談する。1 ラウンドで 4 件を超えた場合は、先に出た 4 件を相談し、残りは次の相談に回す。相談とその修正が終わってもキューにまだ 4 件以上残っていれば、続けて次の 4 件を相談する。4 件未満なら次のラウンドに持ち越す。

相談には AskUserQuestion を使い、1 件の指摘を 1 つの質問にする（1 回で最大 4 問）。

- `question`：何が問題で、どこにあり、直すと何が変わるかを 1〜2 文で。
- `header`：指摘の短い名前（12 文字以内）。
- `options`：直し方の案（推奨を先頭にして「（推奨）」を付ける）と、最後に「見送る」。案は 3 つまで（「見送る」と合わせて 4 つ）。
- 案の違いがコードで伝わるときは `preview` に変更の要点を書く。

回答が返ったら、選ばれた方針どおりに、**そのラウンドの担当エージェント**へ SendMessage で修正を頼む（自動修正と同じ手順で確認し、コミットする）。保留キューには前のラウンドで挙がった指摘も混ざるが、それも今の担当エージェントに頼む。その場合、担当エージェントはその指摘を知らないので、台帳から場所・問題・選ばれた案をすべて書き写して渡す。「見送る」を選んだものは台帳に見送りとして記録し、以後は指摘させない。ユーザーが自由記述で別の方針を書いたら、それに従う。自由記述に「止めて」「終わり」などがあれば、その回答分の修正を終えてからループを終える。

### 5. ラウンドの締め

1. 台帳を更新する。
2. ユーザーに 2〜4 行で経過を伝える：ラウンド番号、自動修正した件数と内容の要点、保留キューの件数、却下した件数。
3. 終了条件（下記）に当たらなければ、次のラウンドの洗い出しを、**新しい担当エージェント**で始める。今の担当エージェントには、以後メッセージを送らない。

## 終了条件

次のどれかに当たったら、ループを終える。

- **中以上の指摘がなくなった**：洗い出しで、重要度が「高」「中」の新しい指摘が 1 件もなかった（重要度は仕分けでメインが確かめたもの。指摘がまったくなかった場合や、却下したものしかなかった場合も含む）。そのラウンドで出た「低」の指摘はふだんどおり仕分け、自動修正のものは直してコミットする。そのあとは保留キューの残りで分かれる。
  - 保留キューが空なら、ここでループを終える（次のラウンドは始めない）。
  - 保留キューに残りがあれば、4 件に満たなくても相談する（4 件を超えていれば 4 件ずつ続けて）。相談で修正を 1 件もコミットしなかった（全件見送りなど）なら、確認ラウンドは回さずにループを終える。修正をコミットしたなら、相談した修正が新しい問題を生んでいないかを見るため、**確認ラウンド**を 1 回、新しい担当エージェントでふだんどおり回す。
  - 確認ラウンドで中以上の指摘が出たら、通常のループに戻る（また中以上がなくなったら、この終了条件を初めから判定する）。
  - 確認ラウンドでも中以上が出なければ、低の自動修正をコミットしたあと、保留キューの残り（確認ラウンドで出た低の要判断を含む）を、最後に 1 回だけまとめて相談する（4 件を超えていれば 4 件ずつ続けて）。その修正を終えたら、確認ラウンドを回さずにループを終える。この最後の相談で入れた修正は、別の担当エージェントの確認を経ていないことを最終報告で伝える。
- **ユーザーが止めた**：「止めて」「もういい」などの指示があった。進行中の修正は最後まで終わらせ、新しいラウンドは始めない。保留キューに残りがあれば、相談するか、そのまま終えるかを聞く。
- **修正が別の問題を生み続けている**：直した箇所に対する指摘が 3 ラウンド続いた。いったん止め、ユーザーに状況を説明して方針を聞く。

## 最終報告

終わったら次をまとめて伝える。

- ラウンド数と、終わった理由
- 確認ラウンドのあとの最後の相談で直した指摘があれば、その一覧と、別の担当エージェントの確認を経ていないこと
- 修正した指摘の一覧（自動修正と、相談して直したものを分けて）
- 見送った指摘と、失敗した指摘（理由つき）
- 保留中のまま終えた指摘（場所・問題・案の要点）。失敗から保留キューに回したまま終えたものは、ここにだけ載せ、「失敗した指摘」には重ねて書かない
- 範囲外の気づき（範囲を指定された場合）
- コミットの一覧（`git log --oneline <開始時のコミット>..HEAD`）と、作業したブランチ名
- テストを走らせた結果。テストのないところは「動作は未確認」と明記する
- push していないこと

## 台帳

台帳はメインだけが書く。担当エージェントには、必要な部分を依頼文に貼って渡す。洗い出しで返ってきた番号（#1, #2, ...）は台帳の ID に置き換えて記録する。洗い出しの報告にある「範囲外の気づき」は、ID を付けずに「範囲外の気づき」の節へ書き写す（同じ内容がすでにあれば書き足さない）。最終報告の「範囲外の気づき」は、この節から作る。「対応済み」の行には、コミットのあとに、担当エージェントが報告したテスト・リンターとその結果（走らせていなければ「なし（動作は未確認）」）を書く。最終報告の「テストを走らせた結果」は、ここから作る。

```markdown
# improve-loop 台帳

- 対象範囲: リポジトリ全体
- 観点: 指定なし
- 開始時のコミット: {準備のときの HEAD}
- 開始時の未追跡ファイル: {準備のときの `git status --porcelain --untracked-files=all` の `??` のパス。なければ「なし」}
- 現在のラウンド: 3（確認ラウンドなら「3（確認ラウンド）」と書く）
- 担当エージェント ID: {このラウンドの担当エージェントの ID}

## 保留キュー（要判断）
- [D-07] 設定ファイルの既定ポートを 8080 から 3000 に変える？ — config/default.toml:12
  - 問題: README と docker-compose.yml は 3000 を前提にしているが、既定値が 8080 のため手順どおりに起動すると繋がらない
  - 案 A) 3000 に統一（推奨）: 利点＝ドキュメントと揃う。欠点＝8080 で使っている既存の利用者は設定の変更が要る
  - 案 B) 環境変数で上書き可能にする: 利点＝既存の利用者に影響しない。欠点＝既定値の食い違いは残る
- [A-05] R3 修正失敗→相談: パスの連結を文字列で行っている — scripts/build.py:30
  - 問題: パス区切りを `/` 決め打ちで連結しており、Windows で動かない
  - 失敗の理由: `/` を `os.path.join` に替えたら、テストが Windows で通らなかった（期待値が `/` 区切り）
  - 案 A) テストの期待値も `os.path.join` で組み立てる（推奨）: 利点＝実装とテストが揃う。欠点＝テストの変更が要る
  - 案 B) `pathlib` に置き換えて `as_posix()` で比べる: 利点＝表記が揃う。欠点＝変更が広がる

## 対応済み

- [D-02] R2 相談→案 B で修正: エラー時の終了コードを 1 に統一 — cli/main.py — 8b47e9d — テスト: pytest tests/test_cli.py 通過
```

ID は、台帳に記録した順の全体の通し番号（洗い出しの番号ではない）に、区分の接頭辞（自動修正 `A-`、要判断 `D-`、却下 `X-`）を付ける。あとで対応済み・見送り・失敗などに移っても、ID は変えない。
